# ansible-cfg

Конфигурация восьми личных серверов (Ubuntu + один Fedora).

## Установка на управляющей машине

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
make deps          # коллекции из requirements.yml в ./collections
```

`ansible.cfg` подхватывается автоматически, если запускать из корня репозитория.

## Рабочий цикл

### Новый сервер

Пользователя `gul` там ещё нет, поэтому первый заход — от root:

```bash
make bootstrap HOSTS=newhost REMOTE_USER=root
```

Это заведёт `gul`, положит ssh-ключ и настроит sudo. Дальше хост живёт как все:
`make check HOSTS=newhost` → `make apply HOSTS=newhost`. Не забыть добавить его
в `inventory/hosts.yml` и в `~/.ssh/config`.

### Повседневное

```bash
make ping                  # связность
make facts                 # что за машины в инвентаре
make lint                  # статическая проверка
make bootstrap HOSTS=happy # разовая подготовка нового хоста
make check HOSTS=oc        # вхолостую, с диффом
make apply HOSTS=oc        # применить на одном хосте
make apply                 # применить везде
```

Правило: **`check` → `apply` на одном хосте → `apply` на всех.** Без исключений
для «мелких» правок.

## Структура

```
ansible.cfg              настройки клиента
inventory/hosts.yml      список серверов и групп
inventory/group_vars/    переменные по группам
site.yml                 главный плейбук: какие роли на каких хостах
playbooks/               одноразовые/диагностические плейбуки
roles/<name>/
  defaults/main.yml      переменные роли, включая развилку по ОС
  tasks/main.yml         что делать
  handlers/main.yml      реакции на изменения (рестарты сервисов)
  templates/             jinja2-шаблоны конфигов
  files/                 файлы, которые роль раскладывает как есть
```

Файлы лежат в `roles/<name>/files/`, а не в общем `files/` в корне: так роль
самодостаточна и находит их независимо от того, откуда запущен плейбук.

### Две вещи, на которых легко обжечься

**Приоритет переменных.** Отличия Ubuntu/Fedora (например, группа `sudo` против `wheel`) лежат в `defaults/main.yml`
словарём вида `common_base_packages_by_os`, а не в `roles/<name>/vars/`.
Причина: `defaults/` — самый низкий приоритет, его свободно перебивает
`host_vars/`; а `vars/` — наоборот, один из самых высоких, и он бы молча
перебил `host_vars/`. Именно так `host_vars/happy.yml` может сказать
«здесь ntpsec, а не chrony», и роль это услышит.

**Факты только как `ansible_facts.*`.** В `ansible.cfg` выставлено
`inject_facts_as_vars = False`, поэтому привычных `ansible_os_family`
и `ansible_distribution` нет — надо писать `ansible_facts.os_family`.
Это будущее поведение по умолчанию (ansible-core 2.24); включено заранее,
чтобы устаревшая форма падала сейчас, а не превратилась в `undefined` потом.
Переменные подключения (`ansible_user`, `ansible_host`) — не факты,
их это не касается.

## Роли

Порядок — тот, в котором они стоят в `site.yml`.

**Плей 1 — обычная конфигурация, все хосты параллельно:**

| # | Роль             | Что делает                                              |
|---|------------------|---------------------------------------------------------|
| 1 | `users`          | пользователь gul, ssh-ключи, беспарольный sudo           |
| 2 | `dotfiles`       | `.profile` и `.vimrc` — только если их нет               |
| 3 | `common`         | пакеты, таймзона, синхронизация времени                  |
| 4 | `local_scripts`  | собственные скрипты в `/usr/local/bin`                   |
| 5 | `apt_updates`    | `check-updates*` в `/usr/local/bin` и `/etc/cron.d/apt-updates` — только Ubuntu |
| 6 | `zabbix_agent`   | пакет из дистрибутива, конфиг шаблоном                   |
| 7 | `mariadb`        | `mysqldump.cnf` в drop-in каталоге MariaDB; зависимость юнита от монтирования datadir |
| 8 | `bitcoin`        | `bitcoin.conf` демона и клиентов; drop-in юнита: зависимость от монтирования, таймаут остановки |
| 9 | `qbitcoin`       | logrotate для логов демона QBitcoin                      |

**Плей 2 — то, что может стоить доступа к машине. `serial: 1`, остановка при
первой ошибке:**

| # | Роль        | Что делает                                                    |
|---|-------------|---------------------------------------------------------------|
|10 | `sshd`      | вход только по ключу, root без пароля                          |
|11 | `udp_link`  | сборка udp-link из исходников, одна версия везде               |
|12 | `firewall`  | полное владение `/etc/iptables/rules.v4` и `rules.v6`           |

Плюс `playbooks/bootstrap.yml` — разовая подготовка хоста: заводит `gul` на
совсем новом сервере (`REMOTE_USER=root`) и доставляет биндинги dnf5 на Fedora.

### Сознательно не делаем

- **`unattended-upgrades` / `dnf-automatic`** — автоустановку не включаем.
  Пакет `unattended-upgrades` роль `apt_updates` ставит, но только ради
  `--dry-run` в `check-updates-security`; что там в `20auto-upgrades` — не
  трогаем.
- **Бэкап** — настроен вручную, в Ansible не заводится.

### Что стоит автоматизировать дальше

| что | почему |
|---|---|
| **fail2ban** | неактивен на ho, конфиг нигде не управляется |
| **vault** | `/etc/zabbix/chain-checkpoint.conf` с паролями RPC живёт вне репозитория |

`site.yml` обязан оставаться пригодным для честного `--check`: всё, что нельзя
выполнить вхолостую, живёт в `playbooks/bootstrap.yml` и запускается разово.

| brr    | Ubuntu 26.04 | KVM-гость     | chrony вместо systemd-timesyncd     |

### Отклонения от общего правила

- **happy: `users_manage_sudoers: false`.** В группе `wheel` там состоят `root`,
  `gul` и `tiger`. Общее правило роли `%wheel ALL=(ALL) NOPASSWD:ALL` выдало бы
  беспарольный root ещё и пользователю `tiger`. Сам `gul` там уже имеет NOPASSWD
  персональным правилом в `/etc/sudoers`, рядом с десятком тонких правил для
  zabbix, backup и rsync — роль туда не лезет.
- **happy: `#includedir /etc/sudoers.d` — это действующая директива**, а не
  закомментированная строка (решётка в ней не означает комментарий; новая форма
  записи — `@includedir`). Роль не пытается её «раскомментировать», а только
  проверяет наличие: `includedir` без префикса — синтаксическая ошибка, которая
  положила бы sudo целиком.
- **ho: `common_manage_time_sync` выключается автоматически** — это контейнер.
- **brr, sin: `common_time_sync_service: chrony`.** Пакета `systemd-timesyncd`
  там нет вовсе (`systemctl` показывает юнит как `not-found`), время ведёт
  chrony. Дефолт роли пытался бы запустить несуществующий юнит. Указано именно
  `chrony`, а не `chronyd`: на Ubuntu второе — алиас, реальный юнит первый
  (на Fedora, у happy, наоборот).
- **brr, sin: `mariadb_required_mounts: [/var/lib/mariadb]`.** Datadir на
  LUKS-томе с `nofail`; без `RequiresMountsFor=` сервер стартовал бы на пустом
  каталоге. Подробности в разделе про MariaDB.
- **brr, sin: `bitcoin_required_mounts` и `bitcoin_stop_timeout_sec: 600`.** Цепочка
  на отдельном LV: на sin это весь `/var/lib/bitcoin`, на brr только
  `/var/lib/bitcoin/blocks` (bind из `/data/bitcoin/blocks`). Без зависимости
  bitcoind стартовал бы на пустом каталоге и начал IBD с нуля. Подробности в
  разделе про bitcoin.
- **spelik: `qbitcoin_logs` с `copytruncate`.** Там оба демона QBitcoin —
  docker-контейнеры, и лог пишет не демон, а systemd: в юните
  `StandardOutput=append:/var/log/qbitcoin.log`, дескриптор держит `docker run`
  всё время работы сервиса. Переименование оставило бы его писать в
  переименованный inode. На node, sin и brr наоборот: демон открывает лог на
  каждую запись и закрывает, поэтому там обычное переименование с `create`.
  Подробности в разделе про qbitcoin.
- **spelik_com: `apt_updates_mailto: root@spelik.com`.** Вывод cron-заданий
  `apt-updates` уходит на доменный root, а не в локальный ящик. На spelik и
  node так было руками, brr и sin получают это вместе с группой; в kiev —
  дефолт cron.
- **happy: `zabbix_agent_manage: false`.** Конфиг агента там по старому пути
  `/etc/zabbix_agentd.conf`, без `Include`, с двумя десятками UserParameter
  плюс `SourceIP`, `ListenIP` и `StartAgents`. Общий шаблон снёс бы всё это.

### Dotfiles

Роль **засевает, а не выравнивает**: кладёт `~gul/.vimrc` и `~gul/.profile`
только если их нет, существующий файл не трогает никогда (`force: false`).

Так сделано осознанно. Файлы на шести хостах разошлись не косметически:
`.vimrc` у ho содержит 67 лишних строк относительно node и не содержит 35 его,
у oc 41/35, у us 54/36, у happy 41/36. `.profile` на spelik — вообще другая
конфигурация со своим `PS1`, `ENV=$HOME/.shellrc` и алиасами `docker exec`.
Перезапись выкинула бы реальную работу; задача же была в другом — чтобы новый
сервер не приходилось обставлять руками.

**`.profile` не создаётся там, где есть `.bash_profile`.** Для login-шелла bash
читает первый существующий из `~/.bash_profile`, `~/.bash_login`, `~/.profile`
и на нём останавливается. На ho, oc, us и happy `.bash_profile` написан руками
и подключает только `.bashrc`, поэтому `.profile` там не читается вовсе — файл
выглядел бы рабочим, ничего не делая. `.bash_profile` роль не трогает.

Сегодня роль не меняет ничего ни на одном хосте — это и есть ожидаемый
результат. Путь «файла нет → создать» проверен отдельно, на временном каталоге.

### MariaDB

Роль кладёт `mysqldump.cnf` в drop-in каталог: `/etc/mysql/conf.d` на Ubuntu,
`/etc/my.cnf.d` на Fedora. Признак «здесь есть MariaDB» — существование этого
каталога, отдельного флага не нужно: на новом сервере файл появится сам, как
только пакет будет установлен. Перезапуск не делается и не нужен — настройки
читает клиент `mysqldump` при каждом запуске.

Работает на ho, node, oc, us. Проверить эффективные значения:
`my_print_defaults mysqldump`.

Два исключения:

- **spelik** — MariaDB там просто не установлена, каталога нет, роль пропускается
  сама, без флага.
- **happy** — `mariadb_manage: false`. Её `/etc/my.cnf` написан вручную и не
  содержит `!includedir /etc/my.cnf.d`, поэтому drop-in там не читается вообще.
  Подключить каталог значило бы разом активировать тринадцать штатных
  федоровских drop-in'ов (galera, spider, cracklib, шифрование, hashicorp,
  провайдеры сжатия) на живой базе, под которой ещё и Zabbix-сервер.

`max_allowed_packet` сведён к **32M**. До этого на node было 16M, на остальных
трёх 32M; выбрано большее, потому что уменьшение лимита ломает дамп таблицы
с крупной строкой, а увеличение безопасно.

**Зависимость от монтирования.** Список `mariadb_required_mounts` (по умолчанию
пустой) превращается в drop-in `/etc/systemd/system/mariadb.service.d/mounts.conf`
с `RequiresMountsFor=`: systemd не запустит сервер, пока каждый из путей не
смонтирован. Нужно там, где datadir лежит на отдельном томе: без зависимости
mariadb стартует поверх пустой точки монтирования и молча заводит новую пустую
базу. После изменения drop-in'а делается только `daemon-reload`, работающий
сервер не трогается — зависимость влияет на следующий запуск. Пустой список
убирает файл; остальные drop-in'ы в каталоге роль не трогает.

Задано на **brr и sin**: `/var/lib/mariadb`. Там это bind из `/vs/mariadb`, а
`/vs` — LUKS-том, который открывается ключом из `/run/fscryptpwd`; и в crypttab,
и в fstab он `nofail`, так что загрузка без ключа проходит, оставляя
`/var/lib/mariadb` пустым каталогом. Оборотная сторона: если тома при загрузке
нет, `mariadb.service` падает с dependency failed, и после ручного открытия тома
его надо запустить руками — `systemctl start mariadb`.

### sshd

Роль кладёт `/etc/ssh/sshd_config.d/10-ansible.conf` с тремя директивами:
`PasswordAuthentication no`, `KbdInteractiveAuthentication no`,
`PermitRootLogin prohibit-password`.

Префикс `10-` существенен. sshd берёт **первое** встреченное значение
директивы, а `Include` стоит в начале `sshd_config` — значит drop-in бьёт
основной файл, а более ранний по имени drop-in бьёт более поздний. Именно
`50-cloud-init.conf` включал `PasswordAuthentication yes` на node и spelik.

Роль проверяет наличие `Include` и падает, если его нет: без него файл не
читался бы вовсе. Конфиг проверяется дважды — `sshd -t -f` на сам файл и
`sshd -t` на всю собранную конфигурацию, — и только потом `reload`. Reload не
рвёт существующие сессии, поэтому после него роль принудительно переподключается
и пингует: старое соединение ничего не доказывает.

### bitcoin

Роль ведёт **только конфиг**. Пользователь, группа, бинарники и systemd-юниты
приезжают из собственного deb-пакета — это то, что пакет умеет; а `bitcoin.conf`
он поставить не может, потому что там пароли RPC, и на каждом хосте свои.

Признак «здесь есть узел» — существование группы `bitcoin`, которую создаёт
пакет. Поставил пакет — роль начала применяться сама. Управляются **ho**
(testnet4) и **node** (mainnet плюс testnet4, два юнита с общим datadir).
happy исключён: там bitcoind из пакета Fedora, юнит читает
`/etc/sysconfig/bitcoin`.

**Пароли не переписываются.** Существующий `/etc/bitcoin/bitcoin.conf` — источник
истины: его пароли уже принимает работающий демон, а смена потребовала бы
рестарта, что на node означает mainnet-узел с 843 GiB цепочки. Роль копирует
этот файл клиентам (`~gul/.bitcoin/` и `/var/lib/zabbix/.bitcoin/`) через
`remote_src`, то есть целиком на самом хосте — иначе пароли прошли бы через
управляющую машину и попали в вывод `--diff`. Свежие пароли генерируются только
если конфига нет вовсе, то есть на новом сервере.

Заодно исправлены права: `~gul/.bitcoin/bitcoin.conf` был **664 на ho**, то есть
пароли RPC читались любым пользователем. Стало 600, каталог 700.

**Drop-in юнита.** Две настройки, которые нужны там, где цепочка лежит на
отдельном томе, роль пишет в
`/etc/systemd/system/<юнит>.service.d/ansible.conf`:

- `bitcoin_required_mounts` (по умолчанию пусто) → `RequiresMountsFor=`: systemd
  не запустит демон, пока каждый путь не смонтирован. Иначе bitcoind поднимается
  на пустой точке монтирования и молча начинает качать цепочку с нуля.
- `bitcoin_stop_timeout_sec` (по умолчанию пусто, то есть пакетные 90 с) →
  `TimeoutStopSec=`. На остановке bitcoind сбрасывает chainstate на диск, на
  mainnet это минуты; 90 с закончились бы SIGKILL и повреждённой базой.
- `bitcoin_wait_ext4lazyinit` (по умолчанию `false`) → `ExecStartPre=`, который
  ждёт, пока из системы уйдёт поток ядра `ext4lazyinit` (достаёт инициализацию
  новой ФС). Это не юнит, поэтому `After=` тут не поможет, и юнит опрашивает
  `pgrep`; если потока нет, проходит сразу. Ждёт не дольше
  `bitcoin_wait_ext4lazyinit_sec` (3600), `TimeoutStartSec` увеличивается на
  столько же. Включено на brr: инициализация плюс bitcoind, читающий блоки,
  забивали диск настолько, что udev убил воркера LUKS-тома и `/vs` не смонтировался.

Если не задано ничего из этого, файла нет. Имя юнита — `bitcoin_service`, по
умолчанию `bitcoind`; на alpha пакет называет его `bitcoin`. После изменения
drop-in'а только `daemon-reload`, работающий демон не трогается.

Раньше то же самое лежало на brr и sin в ручном `override.conf` (файл, который
делает `systemctl edit`). Роль его удаляет: два drop-in'а с одним и тем же
содержимым путают, а забытый ручной перебил бы host_vars.

Задано на **brr и sin**, оба по 600 с. На sin зависимость от `/var/lib/bitcoin`
(весь datadir — LV `vg0/data`), на brr — от `/var/lib/bitcoin/blocks`: там на
отдельном томе только блоки, bind из `/data/bitcoin/blocks` с `nofail`.

### qbitcoin

Роль делает ровно одно: раскладывает `/etc/logrotate.d/qbitcoin`. Демон, его
пользователь и `/etc/qbitcoin.conf` живут вне Ansible; ротации лога не было
нигде и никогда, и это не мелочь — на день, когда роль писалась,
`/var/log/qbitcoin.log` был **11 GiB на node, 10 GiB на sin и 9.7 GiB на
spelik**, все три созданы накануне, и ничто их не подрезало.

Признак «здесь есть QBitcoin» — **существование самого лога**. Не группа, как в
роли `bitcoin`, и не имя юнита: общего признака у парка нет. На node, sin, brr
и ho демон приезжает пакетом и работает от пользователя `qbitcoin`, а на spelik
это docker-контейнер от `qecurrency` — пользователя `qbitcoin` там нет вовсе.
Путь — единственное, что одинаково. Если ни один из перечисленных в
`qbitcoin_logs` файлов не найден, роль не пишет ничего: на oc и us QBitcoin нет,
а на happy работает только testnet, и его ручной `/etc/logrotate.d/qbitcoin`
роль не трогает, потому что `/var/log/qbitcoin.log` там не существует.

**Две разные схемы ротации — потому что лог пишут двумя разными способами.**

- **node, sin, brr, ho** — пишет сам демон (`log = /var/log/qbitcoin.log` в
  `/etc/qbitcoin.conf`), открывая файл на каждую запись и закрывая обратно
  (проверено `lsof`: у узла, пишущего 16 GiB в сутки, дескриптор попался один
  раз на пятнадцать замеров). Значит, обычное переименование безопасно, новый
  файл подхватывается со следующей записи, ни рестарта, ни HUP не нужно.
- **spelik** — пишет systemd: `StandardOutput=append:` в юните, дескриптор у
  `docker run` на всё время жизни сервиса. Здесь только `copytruncate`.

**`create 0644 qbitcoin qbitcoin` — не косметика.** `/var/log` это
`root:syslog drwxrwxr-x`, а пользователь `qbitcoin` не состоит ни в одной группе,
кроме своей. Сам он файл в `/var/log` создать не может: без `create` демон
пережил бы ровно одну ротацию, а дальше писал бы в никуда. На spelik `create`
нет и быть не может — `copytruncate` ничего не создаёт, он копирует и обнуляет
на месте, сохраняя владельца (там это `root:root`), а пользователя `qbitcoin` на
хосте не существует.

**`qbitcoin_log_rotate` — 30, месяц истории.** В день, когда роль писалась, лог
рос на **12 GiB в сутки на node, 16 на sin, 6 на spelik** (brr почти не писал) и
сжимался примерно в семь раз — при таком темпе тридцать копий не поместились бы
на 59-гигабайтный корень sin. Но тот день был аномалией, столько демон обычно не
пишет.

На случай, если повторится: sin — хост без запаса, и упрётся он первым. Тогда
число опускается в host_vars одной строкой. `delaycompress` выключен осознанно:
он держал бы самую свежую копию несжатой целые сутки и здесь ничего не даёт — он
для демонов, которые продолжают писать в старый файл, пока им не подадут сигнал.

Настоящий рычаг всё же не тут: объём делает `debug = 1` в `/etc/qbitcoin.conf`.
Но это решение про демон, а не про ротацию.

**`su root adm` прописан явно**, а не унаследован от глобального в
`/etc/logrotate.conf`. Без него logrotate вообще отказывается трогать лог:
`/var/log` группозаписываем группой `syslog`, а не `root`, и это ровно тот
случай, про который он говорит «parent directory has insecure permissions ...
Set "su" directive». Плюс так файл корректен сам по себе — а это то, что
проверяет `validate: logrotate --debug` в `tasks/main.yml`: validate видит
только этот файл и никогда `/etc/logrotate.conf`. Проверка не формальность:
синтаксическая ошибка в одном фрагменте останавливает разбор и ломает ротацию
**всех** логов хоста, а не только своего. На spelik она же ловит и семантику —
`create ... qbitcoin qbitcoin` там падает с `unknown group 'qbitcoin'`.

### udp-link

Транспорт, через который ходит весь ssh (`ProxyCommand udp-link` в
`~/.ssh/config`). Роль собирает его из исходников
`https://github.com/pgul/udp-link.git` и держит все восемь хостов на одной
версии — сейчас **0.6**, задана в `udp_link_version`.

Репозиторий публичный, поэтому клонируется по https: ключ не нужен, и роль
работает, даже если ssh-агент не проброшен или запуск идёт с другой машины.
Переключить на `git@github.com:pgul/udp-link.git` — одна строка в defaults.

На Ubuntu роль собирает **deb-пакет** (`make debian-package`) и ставит его, так
что бинарник остаётся в `/usr/bin` под управлением dpkg. На Fedora в исходниках
нет rpm-упаковки, поэтому там просто `make` и копирование бинарника.

Пересборка происходит только когда установленная версия не совпадает с нужной.
Источник истины о том, что установлено: dpkg на Ubuntu, файл-отметка
`/usr/local/share/udp-link.version` на Fedora. Отметка засчитывается только
если бинарник действительно лежит на месте — иначе перенос или ручное удаление
молча считались бы «всё в порядке».

Роль стоит во **втором плее**, рядом с файрволом, с `serial: 1` и
`any_errors_fatal`: сломанный udp-link стоит доступа к машине ровно так же, как
сломанный файрвол. Проверено на деле — happy упал на проверке бинарника первым,
и остальные четыре хоста до роли просто не дошли.

**Что нашлось при переводе под Ansible:**

- Версии разъехались: us 0.2, oc 0.3, ho и spelik 0.5, node — ручная сборка
  v0.6 в `/usr/local/bin`, happy — ничего.
- На node ручная сборка в `/usr/local/bin` затеняла бы свежий пакет из
  `/usr/bin`, потому что `/usr/local/bin` в PATH идёт раньше. Роль её убирает.
- На brr и sin то же самое, но в `/usr/sbin` (сборка из `~gul/udp-link`, не под
  dpkg). Каталог тоже идёт в PATH раньше `/usr/bin` — в том числе в PATH
  ssh-сессии, а это как раз тот PATH, из которого стартует удалённый конец
  udp-link. Список таких каталогов вынесен в `udp_link_shadow_paths`.
- На happy `/usr/local/bin` **вообще нет в PATH**, даже в login-сессии.
  Поэтому там `udp_link_prefix: /usr` — иначе бинарник был бы доступен только
  по абсолютному пути.
- `make install` не используется: его цель зашивает путь и вдобавок
  предпочитает `/opt/local/bin`, если он существует, — это верно на Mac и
  неверно на сервере.

### Файрвол

Роль владеет `/etc/iptables/rules.v4` и `/etc/iptables/rules.v6` целиком: два
шаблона генерят два файла, `iptables-restore` и `ip6tables-restore` их заливают.
Управляются шесть хостов — **ho, node, us, oc, brr, sin**. Исключены happy
(правила собраны вручную) и spelik (Docker пишет 24 правила в filter и 11 в nat
на ходу, статическая заливка стёрла бы их до перезапуска dockerd); флаг
`firewall_manage: false` выключает роль целиком, вместе с IPv6.

Файрвол вынесен в **отдельный плей** с `serial: 1` и `any_errors_fatal: true`:
хосты обрабатываются по одному, и первая же неудача останавливает раскатку,
не давая испортить остальные.

**Порты не только «открыт/закрыт».** Кроме `firewall_tcp_ports` (открыть всем)
есть `firewall_restricted_tcp_ports` — словарь «порт: список адресов». На каждый
адрес генерится свой ACCEPT, всё остальное доезжает до финального REJECT. Так
сделан P2P-порт QBitcoin **9555** на node, brr и sin: это не публичный сервис, к
нему ходят только свои узлы. Список адресов лежит один раз в
`group_vars/all/firewall.yml` (`firewall_qbtc_peers`) и подставляется в
host_vars узлов; в нём пять адресов — brr, spelik, node, sin и **ho**
(91.228.147.70, он же `ho.spelik.com`: имя пока не резолвится, хост до сих пор
отзывается как `ho.happy.kiev.ua`, но адрес от появления записи не изменится).

На **ho, oc и spelik** тот же 9555 открыт **всем** — это узлы, до которых
внешние пиры должны доходить. На ho он в `firewall_tcp_ports` и
`firewall_v6_tcp_ports`. На spelik обе строки записаны в host_vars, но **сегодня
ничего не делают**: `firewall_manage: false` выключает роль вместе со всеми её
переменными, и до тех пор, пока вопрос с Docker не решён, порт там открывается
руками (`iptables -I INPUT -p tcp -m state --state NEW --dport 9555 -j ACCEPT`,
и то же для `ip6tables`). При политике `INPUT ACCEPT`, которая на spelik сейчас,
это и так фактическое состояние.

Порт, попавший в `firewall_restricted_tcp_ports`, **нельзя** дублировать в
`firewall_tcp_ports`: общее правило стоит в цепочке позже, но ACCEPT есть
ACCEPT, и порт снова окажется открыт всему миру.

**Защита от потери доступа.** На всех ssh работает через
`nat PREROUTING --dport 922 -j REDIRECT --to-ports 22`; ошибка в этом правиле
отрезает машину. Поэтому роль устроена так:

1. шаблон проверяется через `iptables-restore --test` ещё до записи файла;
2. перед заливкой снимается снимок живых правил и взводится отложенный откат;
3. после заливки ssh-соединение принудительно рвётся (`meta: reset_connection`)
   и следующая задача обязана подключиться заново — открытый сокет
   ControlPersist переживает даже запрет новых подключений, поэтому проверять
   надо именно новым соединением;
4. если подключиться удалось — откат снимается, если нет — через
   `firewall_rollback_seconds` (по умолчанию 300) хост сам возвращает и прежние
   правила, и прежний файл.

**Что нашлось и исправлено при переводе под Ansible:**

- На ho, node, us и spelik было написано `-s 129.159.205.15/24` — ядро понимает
  это как `129.159.205.0/24`, то есть порт 10050 был открыт всей подсети Oracle
  Cloud вместо одного сервера. Стало `/32`.
- На ho `nftables.service` был включён, а его `/etc/nftables.conf` начинается с
  `flush ruleset`. Он и `iptables-persistent` пишут в один движок; файрвол
  переживал загрузку только по везению с порядком служб. Роль выключает
  автозапуск, но **не останавливает** службу: у неё `ExecStop=nft flush ruleset`,
  то есть `systemctl stop` снёс бы весь файрвол вместе с redirect'ом ssh.
- Убраны дубликаты: правило для udp/1194 на us и MASQUERADE в nat на oc были
  записаны дважды.
- Цепочки Docker на oc — мёртвые остатки (служба неактивна, контейнеров нет),
  в шаблон не переносились.
- Цепочка `f2b-sshd` в iptables тоже оказалась остатком старой конфигурации:
  fail2ban здесь банит через nftables, в собственную таблицу `inet f2b-table`,
  которую `iptables-restore` не трогает.
- **9555 был открыт всем** на node, brr и sin. Стало — только своим узлам.
- **49555 на node, brr и sin не слушает никто** — порт был открыт впустую.
  Убран. На node вместо него открыт **19555**: именно на нём висит
  `qbitcoin-testnet.service`, и именно его уже открывает ho. На brr и sin
  testnet не запущен, поэтому 19555 там не открывается.
- **`FORWARD` на us был единственной политикой `ACCEPT` во флоте.** Стало
  `DROP`. Это не косметика: при `ACCEPT` соединение, открытое снаружи в сторону
  VPN-клиента, форвардилось самой политикой, а при `DROP` ему нужно своё
  правило. Поэтому к `-s 10.10.0.0/24` и `-s 10.10.1.0/24` добавлены зеркальные
  `-d` — ровно так, как на oc уже было в обе стороны. Если через us ходит ещё
  какая-то подсеть, не перечисленная в `firewall_forward_rules`, она перестанет
  форвардиться — это первое, что стоит проверить после раскатки.
- На ho `FORWARD` формально `DROP`, но правило `-j ACCEPT` пропускает всё.
  Оставлено как было: ho маршрутизирует OpenVPN (`tun0`, 10.8.3.0/24), и
  разбираться, какие его пути ещё нужны, — отдельный заход.

### Файрвол: IPv6

Раньше IPv6 не был описан нигде, и по факту флот выглядел так: на **us** был
почти полноценный набор (`INPUT DROP`), на **spelik** и **happy** — только
цепочки Docker с политикой `ACCEPT`, а на **oc, ho, node, brr и sin**
`ip6tables-save` не печатал вообще ничего, то есть таблиц v6 не существовало и
IPv6 не фильтровался никак. Важен из них один: **brr** — единственный хост
флота с настоящим глобальным адресом (`2a0c:4ac1:4:2de::a` на `ens3`, с
маршрутом по умолчанию). Все его порты были открыты интернету по IPv6.

Теперь v6 описан явно и по умолчанию закрыт: `INPUT` и `FORWARD` — `DROP`,
`OUTPUT` — `ACCEPT`. **Исходящие соединения работают** за счёт пары
«`OUTPUT ACCEPT` + `RELATED,ESTABLISHED` первым правилом `INPUT`».

**Списки портов v4 и v6 намеренно раздельные** (`firewall_v6_*`). Адрес из
списка для v4 в правиле v6 не запишешь, а служб, которые здесь реально отвечают
на обоих стеках, почти нет — поэтому хост открывает по IPv6 ровно то, что
названо в его `firewall_v6_*`, и ничего сверх. Исключений два, и оба
access-critical: `firewall_v6_ssh_ports` и `firewall_v6_udp_port_ranges` берутся
из v4. Второе не формальность — у `brr.spelik.com` есть AAAA, и `ProxyCommand`
может позвонить по IPv6; закрыть диапазон udp-link по v6 значило бы отрезать
себе доступ ровно к тем хостам, у которых IPv6 есть.

Что шаблон добавляет всегда:

- `-p ipv6-icmp -j ACCEPT` — в v6 это не удобство, как ICMP в v4: на ICMPv6
  держатся neighbour discovery и path MTU discovery, и его блокировка ломает
  стек, а не пинг;
- `-d fe80::/64 --dport 546` — ответы DHCPv6-клиенту; безвредно там, где адрес
  статический или из SLAAC, и разница между рабочим и мёртвым адресом там, где
  нет;
- ту же пару redirect'ов в `nat`, что и v4: 922 → 22, 22 → мёртвый порт.

Откат расширен на оба стека: снимок снимается с `iptables-save` и
`ip6tables-save`, при неудаче возвращаются оба файла и оба набора правил. Один
случай честно не восстановим — там, где таблиц v6 не было, `ip6tables-save`
печатает пустоту, и «прежнего файла» не существует; откат воспроизводит не
пустоту, а то, чем она была на деле: флашит цепочки и ставит политики `ACCEPT`.

**Что закрывается этим изменением:** на brr IPv6 перестаёт быть проходным
двором. На остальных управляемых хостах глобального v6-адреса сегодня нет, так
что набор ложится впрок — но ложится, а не остаётся неописанным.

Оракловая цепочка `InstanceServices` на us и oc сохранена дословно
(`group_vars/all/firewall.yml`), хотя переходов на неё нет. В v6 на us она тоже
есть — и тоже пустая: правила Оракла адресуют 169.254.0.0/16, у которой
v6-аналога нет.

**Списки `firewall_zabbix_agent_sources` различаются по хостам** — они оставлены
такими, какими были, чтобы ничего не сломать. Свести их к одному списку можно,
но это осознанное решение: на node сейчас нет `91.225.123.133`, а на oc нет
`213.133.164.6`.

### Мониторинг

Два Zabbix-сервера: `happy` (= `zabbix.happy.kiev.ua`, 213.133.161.33) и `oc`
(= `zabbix.spelik.com`, 129.159.205.15). Список в `zabbix_agent_servers` сведён
к ним двоим плюс `127.0.0.1`. Раньше по хостам были рассыпаны ещё
`213.133.164.6` (`its.happy.kiev.ua`) и `91.225.123.133`
(`osokorki.happy.kiev.ua`) — если с этих адресов кто-то опрашивает агентов,
вернуть их в `roles/zabbix_agent/defaults/main.yml`.

На brr и sin агент до сих пор стоял стоковый: `Server=127.0.0.1`,
`ServerActive=127.0.0.1`, без `Hostname` — то есть ни один сервер их не
опрашивал. Роль пропишет оба Zabbix-сервера и `Hostname=brr`/`sin`; сами хосты
с такими же именами **нужно завести в Zabbix руками**, иначе активные проверки
не найдут своих итемов. Вторая половина того же: за активными проверками агент
ходит сам на 10051, а на oc этот порт открыт не всем, а по списку адресов
(`firewall_zabbix_server_sources`) — поэтому brr (5.175.211.176) и sin
(153.75.233.174) добавлены туда. Пока их там не было, агенты этих хостов
достучаться до сервера не могли в принципе.

Скрипт `zbx-chain-checkpoint` лежит в `files/bin/` и раскладывается ролью
`local_scripts` на все восемь хостов. Она отдельная, а не часть `zabbix_agent`,
именно потому что на happy та роль выключена, а скрипт нужен и там. Учётные
данные, которые скрипт читает из `/etc/zabbix/chain-checkpoint.conf`, репозиторий
не трогает — это кандидат в ansible-vault, когда до него дойдут руки.

UserParameter'ы живут в `host_vars/<хост>.yml`. Проверки через JSON-RPC на
localhost задаются словарём `zabbix_agent_rpc_checks` («имя: порт») — они
отличались только портом, и одиннадцать почти одинаковых строк свелись к
восьми парам. Всё остальное — в `zabbix_agent_user_parameters` целиком.

`ho` — единственный контейнер в парке, и это влияет на роли: часы принадлежат
хосту (`systemd-timesyncd` не стартует, `ConditionVirtualization=!container`),
а позже так же придётся поступить с файрволом и модулями ядра. Роль `common`
уже это учитывает через `common_manage_time_sync`. Обратная сторона выбора `ho`
полигоном: он наименее типичен, поэтому чистый прогон на нём **не** гарантирует
чистый прогон на остальных пяти.

Все хосты доступны только через `~/.ssh/config` (порт 922, `ProxyCommand udp-link`),
поэтому в инвентаре нет ни `ansible_host`, ни `ansible_port`.

### Обновления apt

Роль `apt_updates` раскладывает два скрипта и один cron-файл на все Ubuntu-хосты.
Условие — `apt_updates_manage: "{{ ansible_facts.os_family == 'Debian' }}"`,
так что happy отпадает сам, без флага в `host_vars`, а новый Ubuntu-хост
подхватывается автоматически.

Скрипты в `roles/apt_updates/files/` — как лежали на хостах, байт в байт:

- `check-updates` — `apt-get upgrade --dry-run` в `/var/tmp/updates-system`,
  затем `zabbix_sender` с ключом `system.updates`. Отправляет он **всегда 0**:
  строка `[ -s "$OUT" ] && RES=1` закомментирована. Полезная нагрузка — сам
  файл, который читает UserParameter `updates-list[system]` на oc и spelik.
- `check-updates-security` — `unattended-upgrade --dry-run` в
  `/var/tmp/updates-security`, код возврата уходит ключом `security.updates`.

`/etc/cron.d/apt-updates` собирается шаблоном: каждые четыре часа autoremove,
purge остатков `rc`, `apt-get update` и `check-updates-security`; `check-updates`
дважды в сутки, в 8:10 и 20:10 UTC. Расписание одно на всех, переменных две:
`apt_updates_mailto` (см. отклонения) и `apt_updates_update_timeout` — `apt-get
update` обёрнут в `timeout 5m`. Раньше так было только на oc, теперь везде:
зависший зеркальный сервер иначе оставляет по подвисшему процессу каждые четыре
часа. Пустое значение убирает обёртку.

Роль ставит `unattended-upgrades` и `zabbix-sender`, потому что без них скрипты
молча не работают; на всех восьми хостах оба уже стояли.

### Принятые решения

- **Файрвол:** iptables, сохранение через `iptables-persistent` (Ubuntu) и
  `iptables-services` (Fedora). Правила — из одного jinja2-шаблона, чтобы модель
  правил была общая; различается только способ сохранения.
- **Zabbix:** пакет `zabbix-agent` из репозиториев дистрибутива. Версии в Ubuntu
  и Fedora разойдутся — конфиг пишем совместимым с младшей из них.
- **Файрвол внедряем последним** и обязательно так: сначала `--check --diff`,
  потом `apply` на одном хосте, **не закрывая вторую ssh-сессию к нему**, пока не
  убедишься, что доступ жив.

## Секреты

Пока их нет. Когда появятся (пароли БД, токены Zabbix, ключи бэкапа):

```bash
echo 'длинный-пароль' > ~/.ansible/vault-pass-ansible-cfg
chmod 600 ~/.ansible/vault-pass-ansible-cfg
# раскомментировать vault_password_file в ansible.cfg
.venv/bin/ansible-vault create inventory/group_vars/all/vault.yml
```

Файл пароля держать **вне** репозитория. В `vault.yml` переменные именовать
с префиксом `vault_`, а в открытых `group_vars` ссылаться на них —
так видно, откуда что берётся.
